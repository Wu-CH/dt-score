# DT-Score project analysis (2026.09.23)

## Scope

I reviewed the project structure, the deployment algorithm in the DT-Score source, the coverage evaluator, and the project documentation.

## Summary

This is a solid research-style C++ implementation of a geometric sensor-placement strategy for a sensing area with obstacles. It combines boundary and obstacle gap filling with a Delaunay-triangulation-based candidate search to improve coverage.

## What the project does well

- Implements a realistic deployment workflow with initial sensors, boundary repair, and obstacle-aware candidate placement.
- Uses a Delaunay-based empty-circle heuristic to identify promising sensor insertion points.
- Separates deployment and coverage evaluation into distinct phases, which is a good design choice for this kind of optimization problem.
- Incorporates a probabilistic sensing model and blockage checks, which makes the algorithm more faithful to real-world wireless sensing than a purely uniform placement approach.

## Main concerns

- The code is highly monolithic, with much of the state kept in global vectors and shared variables.
- There are many hard-coded heuristics and magic numbers, including offset values, grid spacing, and scoring thresholds.
- Performance is likely the biggest risk. The candidate-scoring loop repeatedly checks obstacle intersections across wide grid ranges.
- Numeric robustness is weak because some geometry predicates use exact comparisons such as zero-crossing checks and membership tests.
- Parsing, geometry, scoring, rendering, and output generation are all mixed into the same large source file, which makes maintenance harder.

## Suggested improvements

### 1. Refactor into smaller modules

Split the implementation into clear sections:

- input parsing
- geometry primitives
- obstacle and boundary generation
- candidate scoring
- output generation

This would make the algorithm easier to test and extend.

### 2. Replace global state with a structured configuration object

The current design relies heavily on shared state. A configuration or context object would improve clarity, reduce coupling, and make the system safer to reuse.

### 3. Add epsilon-based numeric guards

Use a tolerance value for geometric predicates instead of exact equality, especially in:

- line intersection checks
- point-on-segment checks
- polygon inclusion checks

This is important because the algorithm depends on repeated geometric tests near obstacle boundaries and triangulation edges.

### 4. Reduce repeated work in the scoring loop

The scoring step is likely the main performance bottleneck. Potential improvements include:

- precomputing obstacle segments once
- caching line-of-sight and blockage checks
- restricting evaluation grids to valid areas only
- avoiding repeated full scans of all obstacles for each grid point

### 5. Add automated validation

The repository already includes sample cases under the test directory, which is useful for regression testing. These could be extended with:

- a regression harness that compares output files
- a coverage monotonicity check across expected scenarios
- unit tests for geometry primitives and obstacle logic

### 6. Improve build tooling

The Makefile is simple but minimal. It would benefit from:

- a CMake-based build
- separate debug and release targets
- compiler warnings enabled by default
- sanitizer support for debugging
- a clearer CLI contract

## Priority order

The highest-value improvements are:

1. Break the main file into smaller components.
2. Harden the geometry calculations with tolerance-based checks.
3. Optimize the candidate-scoring and obstacle-checking loops.
4. Add regression tests using the sample cases.
5. Modernize the build setup.

## Final note

I did not compile or execute the project in this pass because the request was analysis-only and this environment is read-only. This assessment is based on direct source inspection of the project files and their structure.
